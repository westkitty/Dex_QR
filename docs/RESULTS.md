# Test results

Everything below was generated by the scripts in `tests/` on the build box (8-core Linux VM, Node 24, Chrome 156) on 2026-11-01. Raw data is in `results/`, and `node tools/report.mjs` regenerates this file.

**Not tested: real phone or laptop camera scanning.** The closest test is Chrome's fake camera (`--use-file-for-fake-video-capture`) playing a video of the sender's frames, which exercises the receiver's `getUserMedia` path but not optics, focus, glare, rolling shutter or screen flicker. See TEST_CHECKLIST.md.

## How the drop-rate trials were run (read this first)

To make 900 trials per decoder affordable:
1. Each file's sender stream was **rendered once** to PNG frames (`tests/e2e/render-frames.mjs`, the same JS the sender page uses). That is 196, 1,397 and 6,722 frames for 10, 100 and 500 KiB.
2. **Every frame was decoded once** by a real QR decoder (zbar via pyzbar, and separately zxing-cpp), and the decoded strings were cached.
3. Each trial then **replays the cached decoder output** with a random start frame (uniform over the first K frames) and i.i.d. random frame drops at 10%, 30% or 50%. It feeds the strings to the receiver's own `ReceiverSession` (the same JS as receiver.html), and compares the SHA-256 of the rebuilt file with the original.

Because the decoders read 100% of the clean frames, the zbar and zxing tables are identical. Same frames and same RNG seeds give the same results.

Separately, **truly end-to-end runs** (no caching) are listed further down: frames → H.264 video → ffmpeg → zbar → receiver → SHA-256, 3 per drop rate per size. The headless-browser tests run the actual pages.

The test files are **10 KiB, 100 KiB and 500 KiB** (10,240 / 102,400 / 512,000 bytes) of incompressible pseudo-random data. "Minimum" means K, the number of source blocks. You cannot rebuild the file from fewer than K packets.

## Summary

- **Success rate: 100% in every cell.** That is 900/900 trials with zbar and 900/900 with zxing-cpp at 10%, 30% and 50% frame drop. All 27 truly end-to-end video runs passed, and so did all headless-browser tests. Every success was checked as byte-identical by SHA-256.
- **Overhead** (packets used ÷ K), mean, protocol v2: about 1.07–1.08 for 10 KiB (K = 26), 1.006–1.007 for 100 KiB (K = 257), and 1.001 for 500 KiB (K = 1281). Protocol v1 measured 1.11–1.14, 1.01–1.02 and 1.003–1.007 on the same setup (see CHANGELOG.md). It is roughly independent of the drop rate, as expected for a fountain code.
- **Tail:** p95 ≤ 1.24 everywhere, and the worst single trial was 1.31 (10 KiB). Under v1 the worst trials were 1.65 (10 KiB), 1.34 (100 KiB) and 1.23 (500 KiB); v2's degree boost (PROTOCOL.md §3) removes most of that tail, which came from sparse soliton rows leaving the system rank-deficient. Codec-level numbers for both versions are in `results/degree_boost.json`.
- **Wall-clock cost of drops:** at drop rate p, the receiver needs about overhead ÷ (1 − p) × K displayed frames. For example, about 2.0 × K at 50% drop for large files.
