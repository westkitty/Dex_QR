Tuning speed, density, security
Slower and sparser codes are easier for weak cameras; faster and denser codes finish sooner. Speed, error correction and module size apply live; density needs Prepare.
Packs the file with the browser's built-in deflate before sending, so text, CSV, JSON and source files need far fewer frames. It is skipped automatically for files that do not shrink (JPEG, ZIP, video). With a passphrase, compression happens before encryption, so the stream's length hints at how compressible the file is; untick this if that matters (see the threat note).
With a passphrase, one small key-check frame is shown every 32 frames (about 3% longer stream), so a wrong passphrase is reported within seconds instead of after the whole file. It carries a 2-byte check value, not the key; it lets someone who films a single frame start guessing passphrases offline (they still need the whole stream to confirm one). Untick for the old behaviour.
Every passphrase guess costs an attacker one full key derivation. "Tuned" measures this device and picks the count that takes about one second here (at least 600,000, at most 8,000,000), so each guess costs up to 13× more than the standard count. The receiver derives the key once with the same count; a phone may take a few times longer than this computer. Used only with a passphrase.

Keys: Space or K play/pause, F full screen, Esc leave it. The code flashes black and white at the chosen speed (8 per second by default); if flashing light bothers you, look away while it plays or lower the speed. The page's own animations are slow fades, a 6-second how-to loop beside the code and a one-time check mark when the receiver's Done code is confirmed (nothing flashes); turn them off with the motion button at the top.

How to receive

  1. On the other device, open Receive and press Start scanning.
  2. Point its camera here from 20–40 cm, with the whole code in view.
  3. Hold steady until it says Done. Missed frames are fine.

Tip: turn this screen's brightness up.
